# План: первичное ревью проекта

- Задача: [Tarolrr/airogue#1 — Первичное ревью проекта](https://github.com/Tarolrr/airogue/issues/1).
- Базовая ветка: `main`.
- Тип работы: ревью и документация для последующей автоматизированной разработки.
- Этот PR содержит только план; перечисленные ниже изменения документации выполняются при реализации задачи.

## Проблема

Новому разработчику или автоматизированному агенту не хватает достоверной точки входа в проект. Корневой `README.md` пуст, корневой `AGENTS.md` отсутствует. Существующая документация смешивает реализованное поведение, проектные намерения и исторические рекомендации.

Предварительный осмотр выявил конкретные расхождения:

- `docs/ARCHITECTURE.md` описывает `utils/` и `llm/components.py`, которых нет в текущем дереве, и ссылается на отсутствующий `LLM_GUIDELINES.md`.
- `project_analysis.md` описывает старую схему генерации и модель, тогда как в `llm/generators/` уже есть специализированные генераторы.
- `tests/README.md` содержит исторический результат «4 passed, 4 skipped» и неполный список тестов; его нельзя считать текущей проверкой работоспособности.
- `pyproject.toml` задаёт Python `^3.10`, Poetry и зависимости, но инструкции тестирования ориентированы на отдельный Windows venv. Порядок установки и запуска требует сверки.
- В `tests/conftest.py` имеются ссылки на отсутствующий `utils.validation`; наличие фикстур не доказывает работоспособность всех сценариев. Правила маркировки тестов также требуют проверки перед заявлением об автономном запуске без API.

Эти наблюдения получены статическим чтением. Работоспособность приложения и тестов на этапе планирования не подтверждалась.

## Цели и границы

1. Провести ревью всей существующей Markdown-документации и сопоставить технические утверждения с кодом, конфигурацией и тестами.
2. Заполнить `README.md`: назначение проекта, состояние реализации, установка, запуск, тестирование и навигация по документации.
3. Создать корневой `AGENTS.md` с проверяемыми инструкциями для автоматизированной разработки.
4. Устранить противоречия и неработающие ссылки, сохранить полезные архитектурные сведения и явно отделить планы от реализованного поведения.

Использовать канонические имена `AGENTS.md` и уже существующий `README.md`, несмотря на строчное написание в задаче. Не создавать параллельные `agents.md`/`readme.md`.

Вне рамок: исправление игровой логики, рефакторинг генераторов, реализация отсутствующих модулей, обновление зависимостей и lock-файла, создание CI, новых тестовых инфраструктур или игровых возможностей. Найденные дефекты кода фиксируются как последующие задачи в отчёте, а не исправляются в рамках документационного ревью.

## Подход

### 1. Инвентаризация и проверка источников

Прочитать `project_analysis.md`, все документы в `docs/`, `tests/README.md` и существующие правила `.windsurf/rules/llm-guide.md`. Сверить их с `pyproject.toml`, `poetry.lock`, `main.py`, `g.py`, модулями `game/`, `llm/` и реальным составом `tests/`.

Сохранить результаты в `docs/PROJECT_REVIEW.md`: для каждого проверенного документа указать статус, обнаруженное расхождение, подтверждающий путь или символ в коде и принятое исправление либо отложенный вопрос. Различать подтверждённые факты, проектные намерения и непроверенные предположения. Не объявлять текущую реализацию правильной только потому, что она существует: расхождение с контрактом отражать явно.

### 2. README для разработчика

Заполнить существующий `README.md` следующими разделами:

- Назначение AiRogue: roguelike на TCOD/ECS с LLM-генерацией контента; честное описание стадии проекта.
- Краткая карта репозитория и путь от генерации мира к игровым сущностям.
- Поддерживаемый Python согласно декларации проекта, установка через Poetry с использованием lock-файла, запуск команд из корня репозитория. Проверить необходимость `poetry install --no-root` с учётом структуры проекта и записать фактически проверенный вариант.
- Запуск игры через `poetry run python main.py`: необходимость графического окружения и доступность tilesheet из `data/`.
- CLI генерации через `poetry run python -m llm.generators.cli`: проверенные аргументы, настройка ключа через поддерживаемый механизм и пояснение, какие операции обращаются к внешнему API. Не включать реальные секреты или личные настройки.
- Проверенный порядок запуска тестов без сетевых вызовов; отдельно описать необязательные сценарии с реальным API и ограничения проверки.
- Ссылки на `AGENTS.md`, архитектуру, контракты, отчёт ревью и актуальные дальнейшие шаги.

Не обещать поддержку платформ, моделей или полностью работающий quickstart без проверки. Если запуск заблокирован существующим дефектом, указать воспроизводимый симптом и ограничение.

### 3. AGENTS для автоматизированной разработки

Создать короткий корневой `AGENTS.md`, распространяющийся на весь репозиторий:

- Порядок знакомства с README, отчётом ревью, архитектурой и контрактами; ссылки вместо копирования больших документов.
- Карта ответственности `game/`, `llm/generators/`, `llm/models.py`, провайдеров, глобального состояния и тестов.
- Команды установки и верификации, согласованные с README; не ссылаться на отсутствующие линтеры, hooks или CI как на настроенные проверки.
- Рабочий цикл: проверить исходное состояние, ограничить изменения задачей, сверить затрагиваемые контракты и вызывающий код, выполнить подходящие проверки и описать результат.
- Сохранение ECS-инвариантов и TCOD lifecycle; согласованное изменение моделей, генераторов и потребителей; проверки поведения при изменении кода.
- Правила для LLM: использовать моки для локальных проверок, не запускать платную генерацию как обязательную документационную проверку, не сохранять ключи и приватные данные в репозиторий.
- Отдельная фиксация исходных падений и недоступных проверок; запрет выдавать пропущенную проверку за успешную или скрывать дефект отключением теста.

Согласовать инструкции с полезными существующими правилами Windsurf. Убрать противоречащие или устаревшие указания в документации, не добавляя зависимость от конкретного редактора или обязательного ручного подтверждения каждого изменения.

### 4. Согласование документации

Точечно обновить `docs/ARCHITECTURE.md`, `docs/MODULE_CONTRACTS.md`, `docs/NEXT_STEPS.md`, `docs/TROUBLESHOOTING.md`, `tests/README.md` и `project_analysis.md` там, где ревью подтвердит ошибку. Нереализованные компоненты обозначить как планируемые; исторические сведения удалить, актуализировать или явно пометить. Заменить ссылки на отсутствующий документ инструкций ссылками на `AGENTS.md` с корректными относительными путями.

Основной язык обновляемых документов — английский, как в существующей документации; названия файлов, символов и команды сохраняются дословно. Не переписывать документы целиком только ради стиля.

## Риски и меры

| Риск | Мера |
| --- | --- |
| Документация обещает больше, чем реализовано | Каждое ключевое утверждение связать с кодом; планы выделить отдельно. |
| Тесты неожиданно обращаются к API | До запуска проверить фикстуры, маркеры и точки создания клиентов; не считать одного фильтра по маркеру достаточной гарантией. |
| Установка или тесты падают из-за исходных дефектов | Записать команду и результат в отчёте; не расширять задачу до исправления кода и зависимостей. |
| Игра недоступна в окружении без дисплея | Отделить статическую проверку от ручного GUI smoke-test и явно указать непроведённую проверку. |
| Новые инструкции конфликтуют со старыми | Согласовать README, AGENTS, тестовый гайд и правила редактора; использовать ссылки на единый источник. |
| Ревью превращается в реализацию roadmap | Ограничить изменения Markdown-файлами; технические дефекты перечислить как последующую работу. |

## Валидация и критерии приёмки

- [ ] В `docs/PROJECT_REVIEW.md` учтены все существующие документы и правила редактора; у каждого замечания есть доказательство и решение либо явная причина откладывания.
- [ ] Корневые `README.md` и `AGENTS.md` заполнены и согласованы; дубликатов с другим регистром нет.
- [ ] По README можно определить назначение проекта, требования, порядок установки, команды запуска и проверки, а также известные ограничения.
- [ ] AGENTS позволяет будущему агенту выбрать файлы для изменения и подходящую проверку без выдумывания команд или архитектурных сущностей.
- [ ] Все относительные Markdown-ссылки и упомянутые пути проверены; несуществующие элементы явно обозначены как будущие.
- [ ] Команды установки и безопасные команды справки проверены в изолированном окружении, либо причина невозможности проверки записана. Зависимости и lock-файл не изменены.
- [ ] После проверки отсутствия сетевых вызовов выполнен подходящий набор существующих тестов через Poetry; записаны фактические результаты, исходные ошибки и пропуски. Если безопасный набор выделить нельзя, зафиксирован блокер вместо запуска с реальными ключами.
- [ ] Необязательные API/GUI-проверки отделены от локальных; исторические числа успешных тестов не выдаются за текущие результаты.
- [ ] Итоговый diff содержит только документацию в рамках задачи, без секретов, сгенерированных миров и изменений runtime-кода; `git diff --check` проходит.

Для PR с данной спецификацией достаточно проверки структуры плана, соответствия задаче и `git diff --check`: выполнение тестов приложения не подтверждает корректность документационного плана.
