# План: поддержка подписки Codex

- Задача: [Tarolrr/airogue#9 — Поддержка подписки codex](https://github.com/Tarolrr/airogue/issues/9).
- Базовая ветка: `main`.
- Этот PR содержит только спецификацию; реализация относится к следующей итерации.

## Проблема

Сейчас весь production-путь генерации привязан к `langchain_openai.ChatOpenAI`: `BaseGenerator.llm` создаёт его с `OPENAI_API_KEY`/`--api-key`, а `WorldGenerator` передаёт этот аргумент всем пяти специализированным генераторам. CLI заранее прекращает работу, если ключа нет. Поэтому пользователь с действующей ChatGPT/Codex-подпиской, но без оплачиваемого Platform API key, не может запускать генерацию и расходовать включённое в подписку использование Codex.

OAuth не следует добавлять в приложение. Официальная документация различает ChatGPT login, который даёт подписочные преимущества *клиентам Codex*, и API key, который оплачивается по тарифам Platform API; для обычных OpenAI API-вызовов она предписывает Platform API key. Значит, браузерный OAuth в Python не сделал бы существующий `ChatOpenAI`-вызов подписочным и добавил бы хранение/refresh секретов, callback и UI без поддерживаемого целевого API.

Выбран `codex app-server` (локальный JSON-RPC процесс, далее «Codex backend»): он предназначен для встраивания Codex threads/turns в собственный клиент и использует уже выполненный `codex login` с ChatGPT account либо `CODEX_ACCESS_TOKEN`. Это наименьшее изменение относительно имеющегося синхронного генератора: Python-адаптер превращает один prompt в один Codex turn и возвращает текст final assistant message в существующую LCEL-цепочку. Не добавлять самодельный OAuth, не читать/не копировать `~/.codex/auth.json` и не передавать ChatGPT cookie в код приложения.

Официальные источники, проверенные при планировании:

- [Authentication](https://learn.chatgpt.com/docs/auth): ChatGPT login использует подписочные преимущества в Codex CLI, а API-key login тарифицируется как Platform API.
- [Access tokens](https://learn.chatgpt.com/docs/enterprise/access-tokens): App Server может использовать уже созданный Codex login или `CODEX_ACCESS_TOKEN`; токен предназначен только для доверенных локальных автоматизаций.

## Цели и границы

1. Добавить явный opt-in backend `codex`, чтобы генераторы могли работать через локально установленный и уже аутентифицированный Codex App Server без `OPENAI_API_KEY`.
2. Сохранить существующий backend `openai` и все его API-key интерфейсы как default, чтобы пользовательские скрипты и offline-моки не изменили поведение.
3. Сохранить текущие prompt templates, `StrOutputParser`/JSON parser и публичные методы генераторов: backend должен быть взаимозаменяемым на границе `BaseGenerator.llm`.
4. Дать пользователю понятную preflight-диагностику и документацию: как установить Codex, выполнить интерактивный login вне приложения, выбрать backend и распознать недоступную подписку/CLI.

Вне задачи: собственный OAuth flow, обмен/хранение/refresh ChatGPT credentials, обход лимитов подписки, облачные Codex tasks, удалённый WebSocket App Server, автоматическое скачивание/обновление Codex, `CODEX_ACCESS_TOKEN` в репозитории/`.env`, изменение игрового/ECS-контракта и реальная платная генерация в CI. App Server является experimental API, поэтому не обещать долгосрочную protocol stability или замену Platform API для остальных OpenAI integrations.

## Подход

### 1. Зафиксировать transport-контракт Codex backend

Добавить, например, `llm/providers/codex_app_server.py` с небольшим синхронным адаптером на стандартных `subprocess`, `json`, `threading`/очереди и LangChain `Runnable`/`AIMessage` из уже установленных зависимостей. Не добавлять новую Python-зависимость и не трогать `poetry.lock`.

При первом `invoke` адаптер запускает `codex app-server --stdio` как дочерний процесс с stdin/stdout pipes, выполняет JSON-RPC `initialize`, создаёт отдельный thread и запускает turn с текстом, полученным из `ChatPromptValue`/сообщений. Он читает JSONL до terminal notification/response turn, извлекает только завершённый assistant message и возвращает объект того типа, который ожидают текущие output parsers. У каждого вызова — новый thread; контекст одного шага (`theme → title → plot`) уже передаётся prompt-ом, а отсутствие скрытого thread state делает результат и тесты предсказуемее.

Protocol implementation сверить с JSON Schema, генерируемой **минимально поддерживаемой** версией `codex app-server generate-json-schema`; зафиксировать эту версию как supported minimum в документации. В частности, реализация должна сопоставлять request IDs, обрабатывать notifications вперемешку с responses, ждать успешного завершения turn, а не первый text delta, и закрывать stdin/terminate/wait процесс при `close()` и при ошибке. Не опираться на незафиксированные внутренние файлы Codex.

Сделать bounded failure modes: таймаут запуска/turn, EOF или malformed JSON, non-zero exit, JSON-RPC error, отсутствие final assistant text и неожиданный server request становятся отдельными понятными исключениями с командой/следующим действием, но без секретов, prompt contents или полного server stderr. Отвечать отказом на tool/approval requests: задача просит только генерацию текста и backend не должен разрешать Codex читать, писать или выполнять команды в пользовательском проекте. Ограничить сохранение stderr в памяти и никогда не наследовать/логировать `CODEX_ACCESS_TOKEN`.

### 2. Выбрать backend в существующей генераторной границе

Расширить `BaseGenerator.__init__` параметрами `provider: Literal["openai", "codex"] = "openai"` и необходимыми настройками Codex (команда `codex`, timeout, опциональный model), сохранив `api_key`, model и temperature для OpenAI без изменения default. В `llm` property:

- `openai` оставляет сегодняшний `ChatOpenAI(model=..., temperature=..., api_key=...)` без запуска Codex;
- `codex` создаёт описанный runnable и не читает/не требует `OPENAI_API_KEY`; если модель/temperature не поддерживается protocol, задокументировать и либо явно отклонить несовместимую настройку, либо не передавать её — не создавать ложное соответствие параметров.

Пробросить `provider` через `ThemeGenerator`, `TitleGenerator`, `PlotGenerator`, `MechanicsGenerator`, `ItemGenerator`, `WorldGenerator` и compatibility wrapper `World`; все вложенные генераторы получают идентичный выбор. Сохранить lazy initialization: `--help`, импорт и конструктор без generation не стартуют subprocess и не требуют login. Удалить предположение CLI, что API key обязателен всегда: проверка ключа применяется только при `--provider openai`.

### 3. Добавить явный и безопасный CLI UX

В `llm/generators/cli.py` добавить `--provider {openai,codex}` (default `openai`), `--codex-command` и `--codex-timeout` с консервативными defaults; передавать выбор в `generate_world`/`WorldGenerator`. При `openai` сохранить текущие `--api-key`, environment-file и precedence. При `codex` не считывать API key как prerequisite, проверить доступность исполняемого файла и показать короткую инструкцию `codex login` при неаутентифицированном/недоступном App Server. Не запускать browser login автоматически: он интерактивен, меняет credential store и не подходит для библиотечного вызова.

Обновить `README.md` и `tests/README.md`: обе схемы аутентификации, пример `poetry run python -m llm.generators.cli --provider codex --output world_model.json`, требование локального trusted machine и существующего `codex login`, различие между subscription и API billing, experimental limitation, секретная природа access token и сохранение запрета сети для default tests. Не добавлять реальные команды login/token или любой token в tracked файлы.

### 4. Проверить адаптер и отсутствие регрессии

Добавить unit-тесты transport-а с fake `Popen`/потоками JSON-RPC: правильный порядок `initialize → thread/start → turn/start`, correlation IDs, финальный ответ после нескольких notifications/deltas, cleanup, timeout, malformed response, process exit, JSON-RPC error и unexpected approval/tool request. Проверить, что error text не содержит установленный в тесте fake `CODEX_ACCESS_TOKEN`.

Добавить тесты выбора backend: OpenAI по умолчанию по-прежнему патчит `llm.generators.base.ChatOpenAI`; Codex создаётся только при invoke; API key не передаётся Codex adapter; `WorldGenerator` передаёт provider всем children. Обновить `tests/test_cli.py` для обеих веток: OpenAI всё ещё отказывает без ключа, Codex запускает generation без ключа и передаёт параметры; `--help` не создаёт process. Использовать моки в месте создания subprocess, не настоящую подписку/CLI.

Default offline suite должен остаться без сети. Исключить live subscription smoke test из CI и сделать его только ручным documented acceptance check на доверенной машине, где пользователь уже выполнил `codex login`: с `--provider codex` получить и сохранить валидный `WorldModel`; отсутствие прав/лимит/CLI даёт диагностическую ошибку, а не fallback на API key и не частичный JSON.

## Риски

| Риск | Мера |
| --- | --- |
| App Server experimental, schema меняется | Зафиксировать minimum Codex CLI, реализовать только стабильный минимальный JSON-RPC flow и тестировать schema/поведение этой версии; при несовместимости дать upgrade error. |
| Codex — агент, а не raw chat completion; ответ может нарушать JSON/text format | Сохранить точные prompts и текущие parsers, вернуть только final assistant message, добавить parser/error tests; не маскировать invalid output. |
| Пользователь ожидает, что OAuth для API расходует подписку | Документация и CLI явно разделяют API-key/OpenAI backend от ChatGPT-authenticated Codex backend; OAuth не реализуется. |
| Prompt запускает локальные tools или меняет проект | Запрашивать текстовый ответ, использовать read-only/deny policy, отвечать отказом на approval/tool requests и тестировать этот путь. |
| Утечка login/access token через stderr, exception или `.env` | Не читать credential files, не печатать env/stderr/prompt; redaction tests; `CODEX_ACCESS_TOKEN` только во внешнем secret store доверенной машины. |
| Новый процесс зависает/остаётся после CLI | Таймауты, bounded output, `finally` cleanup и tests на success/error/timeout. |

## Валидация и критерии приёмки реализации

- [ ] `--provider openai` (и default) сохраняет текущую API-key семантику и не запускает Codex.
- [ ] `--provider codex` работает без `OPENAI_API_KEY`, используя уже аутентифицированный локальный Codex App Server; библиотека не реализует и не хранит OAuth.
- [ ] Adapter корректно проходит initialize/thread/turn JSON-RPC, коррелирует IDs, получает именно terminal assistant output и всегда очищает subprocess.
- [ ] Нет сети, API key, browser login или real Codex запуска в unit/CI; mocks проверяют success и все перечисленные error paths.
- [ ] Codex backend не допускает tool/approval requests и не раскрывает fake access token в диагностике.
- [ ] CLI `--help`, документация и параметры обоих backends соответствуют реализации; `README` не обещает, что Platform API расходы покрываются подпиской.
- [ ] Ручной opt-in smoke check на доверенной login-машине документирован и создаёт валидный `WorldModel`; он не является CI критерием и не запускается без явного действия владельца.
- [ ] Полный offline suite, CLI help, узкий Flake8 и `git diff --check` проходят; нет lockfile churn, ключей, generated world или несвязанных ECS-правок.

Целевые команды после реализации:

```bash
poetry install --no-root
poetry run python -m pytest tests/ -v --ignore=tests/test_world_generator_e2e.py
poetry run python -m llm.generators.cli --help
poetry run flake8 . --select=E9,F63,F7,F82 --exclude=.git,.venv,scratch.py,game/pipeline.py,game/slots.py,llm/models.py
git diff --check
```

Ручная, потенциально расходующая подписочный лимит проверка допускается только после отдельного `codex login` владельца и не выполняется агентом/CI:

```bash
poetry run python -m llm.generators.cli --provider codex --output world_model.json
```
