# План: CI и проверка запуска игры

- Задача: [Tarolrr/airogue#4 — CI, тесты](https://github.com/Tarolrr/airogue/issues/4).
- Базовая ветка: `main`.
- Этот PR содержит спецификацию; workflow, тесты и исправления ниже относятся к последующей реализации.

## Проблема

В репозитории нет CI, поэтому изменения человека и looper могут попадать на ревью без воспроизводимых проверок. По состоянию `a42253b` успешный baseline не установлен. [Руководство по тестированию](../tests/README.md) и [первичное ревью](../docs/INITIAL_REVIEW.md) описывают ограничения, подтверждаемые исходниками:

- `tests/conftest.py` содержит устаревшие фикстуры, а часть тестов патчит `llm.world.ChatOpenAI` вместо места использования `llm.generators.base.ChatOpenAI`. Есть `assert True`, пустые проверки и пропущенные интеграционные сценарии.
- Hooks включения реальных API-тестов находятся в `tests/test_world_generator_e2e.py`, а не в pytest-плагине. Автоматический маркер по имени теста не гарантирует изоляцию сети.
- `main.main()` создаёт TCOD console, загружает tilesheet, вызывает `new_world()`, рисует кадры и обрабатывает события в бесконечном цикле. Сейчас теста этого жизненного цикла нет.
- `game/world_tools.py` требует отсутствующий `world_model.json`, создаёт `World(None)` с обращением к LLM-клиенту и ожидает `Game`, `signals` и `slots`, которых генератор/схема не обеспечивают. Подмена только LLM не делает старт рабочим.
- `InGame.on_event()` распаковывает запрос `Q.all_of(components=[])` в единственную сущность до обработки `Quit`. При нескольких сущностях закрытие окна может завершаться посторонней ошибкой.
- В зависимостях уже есть pytest, pytest-cov, Black и Flake8; Ruff отсутствует. Lock-файл создан Poetry 1.8.2, минимальная версия Python — 3.10.

Старые архитектурные документы не являются источником готовых контрактов. Зелёный тест игрового цикла с тестовым Registry не будет означать, что генерация JSON и его загрузка в игру уже работают вместе.

## Цели и границы

1. Обязательный, воспроизводимый CI для push в ветки и PR в `main`, включая ветки и PR looper.
2. Обычный набор тестов работает без ключей, платных запросов, дисплея и локального мира; неожиданный сетевой вызов приводит к ошибке.
3. Проверяется реальный вход `main.main()`: инициализация, отрисовка, доставка события и освобождение контекста при завершении.
4. Небольшой набор понятных проверок качества с одинаковыми командами локально и в CI.

Вне задачи: завершение модели сигналов/слотов, полноценная интеграция генератора с ECS, игровая механика, live-LLM CI, публикация пакета, матрица всех ОС/Python и массовое форматирование. Допустимы небольшие runtime-исправления, непосредственно необходимые для проверяемого старта/выхода, с регрессионными тестами. Если зелёный набор требует переработки схемы, это блокер реализации с отдельным описанием, а не повод отключать тесты.

## Подход

### 1. Установить честный baseline и изоляцию

Использовать Python 3.10, Poetry 1.8.2 и `poetry install --no-root`. До изменения поведения записать результаты безопасного существующего набора, failures/errors/skips и причины. Сначала проверить места создания клиентов и запретить сеть; не запускать потенциально сетевые тесты с реальными ключами. Не обновлять runtime-зависимости ради прохождения установки.

В `tests/conftest.py` перенести регистрацию `requires_openai_api`, опцию `--run-requires-openai-api` и управление API-тестами. По умолчанию такие тесты не исполняются, даже если ключ случайно доступен; opt-in остаётся только для отдельного ручного запуска. CI дополнительно сохраняет явное исключение `tests/test_world_generator_e2e.py`. Убрать классификацию API-вызовов по подстроке имени; использовать явные маркеры.

Добавить общий запрет исходящих сетевых соединений в offline-тестах, например через зафиксированный в dev-зависимостях pytest-socket, включённый до collection. Защита должна охватывать импорт, setup и выполнение; сетевые проверки внутри subprocess требуют собственного запрета либо должны быть исключены из таких сценариев. Тесты CLI должны изолировать `.env` и пользовательский env-файл, использовать временный каталог и подменять клиента до его создания. Не выдавать отсутствие ключа за сетевую изоляцию. Сам запрет проверить попыткой соединения без отправки реального запроса.

Исправить моки и данные по действительным контрактам, не патчить весь тестируемый метод ради проверки его же возвращаемого значения. Тест требования ключа сохранить как отдельную проверку настоящего конструктора с очищенным окружением, без глобального мока, меняющего его смысл. Заглушки удалить с объяснением отсутствующего поведения либо заменить содержательными сценариями; существующие пропуски перечислить отдельно. Не добавлять `skip`, `xfail`, `continue-on-error` или исключения падающих модулей для получения зелёного CI. Неподдерживаемую интеграцию загрузчика проверять как известную ошибку с конкретным исключением, не называть её успешным запуском.

### 2. Проверить игровой жизненный цикл без дисплея

Добавить `tests/test_game_startup.py` и компактную фикстуру настоящего `tcod.ecs.Registry`: игрок и видимая сущность с `Position`, `Graphic`, `OnMap`. Подменить `game.world_tools.new_world` на фабрику этой фикстуры; явно указать, что загрузчик и генерация находятся за границей данного smoke-теста. Не создавать фиктивные сериализуемые `signals`/`slots` ради прохождения загрузчика.

Вызвать настоящий `main.main()` с настоящими `InGame` и offscreen `tcod.console.Console`. Tilesheet по возможности загрузить из репозиторного PNG. Подменить только создание оконного контекста и источник событий; очередь выдаёт `tcod.event.Quit()` после первого кадра. Проверить:

- фабрика мира вызывается и её Registry установлен в `g.world`;
- выполняются очистка, `on_draw` и `present`, а glyph/координата тестовой сущности действительно появляются в буфере;
- `Quit` доходит до настоящего обработчика и вызывает ожидаемый `SystemExit`, контекст получает `__exit__`;
- исключение из `present` также освобождает контекст и не поглощается;
- исчерпание тестовой очереди немедленно завершает тест ошибкой, чтобы сломанный выход не зависал; глобальные `g.world`/`g.context` восстанавливаются между тестами.

Минимальное исправление в `game/states.py`: обрабатывать `Quit` до запросов к игровым компонентам. Регрессия должна использовать Registry с несколькими сущностями, иначе существующая ошибка распаковки останется незаметной. Исправление движения и runtime-компонентов не включать в этот smoke-test. Если потребуется выделить фабрики для инъекции зависимостей в `main.py`, сохранить обычный интерфейс `main()` и не добавлять отдельный production-режим «CI».

Это покрывает старт цикла, кадр и закрытие; реальное SDL-окно и путь `new_world()` остаются отдельными ограничениями. Xvfb/проверку настоящего окна можно добавить позже, когда появится воспроизводимый игровой мир.

### 3. Добавить GitHub Actions

Создать `.github/workflows/ci.yml` с постоянными job names `tests` и `lint`:

- `push` во все ветки, без ограничения префиксом looper; исключить tag-only запуски через веточный фильтр `['**']`.
- `pull_request` в `main` с обычными событиями открытия, обновления и повторного открытия; запускать также draft PR, не фильтровать bot actor и пути.
- `workflow_dispatch` для диагностики. Дубли push/PR в первой версии допустимы.
- Ubuntu 22.04, Python 3.10, фиксированная версия Poetry; при несовместимости старого lock-файла сначала зафиксировать конкретную причину.
- `permissions: contents: read`, checkout без сохранения credentials, actions закреплены полным commit SHA с комментарием версии. Не использовать `pull_request_target` для исполнения кода PR и не передавать секреты в тестовые jobs. Основание: [GitHub Secure use](https://docs.github.com/en/actions/reference/security/secure-use).
- `timeout-minutes: 10`; concurrency по workflow, событию и PR number/ref с отменой устаревшего запуска. Push не должен отменять проверку PR, ожидаемую при merge.
- Кэш Poetry по ОС/Python/версии Poetry и хешу `poetry.lock`; попадание в кэш не заменяет `poetry install --no-root`.
- Тестовый job запускает весь offline-набор, coverage для `main`, `game`, `llm` и настоящий `python -m llm.generators.cli --help`. JUnit и coverage XML сохраняются с `if: always()`, коротким сроком хранения, без env-файлов и сгенерированных миров. Порог общего покрытия пока не вводить: обязательны конкретные сценарии, процент нужен для диагностики.

### 4. Обеспечить запуск для looper

Проверить, каким способом looper делает push и открывает PR, не выводя credentials. Фильтр имени ветки не решает ограничения GitHub: push через workflow `GITHUB_TOKEN` не запускает следующий workflow; по текущей документации события PR `opened`/`synchronize`/`reopened` могут создавать runs, требующие approval. Для автономного запуска нужен отдельный GitHub App installation token либо подходящий PAT в окружении looper, а не в test job. См. [GitHub: GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token).

Настройка авторизации runner — внешняя предпосылка, а не изменение кода AiRogue. Если прав недостаточно, явно записать блокер и требуемое действие владельца. Не считать отсутствие run успешной проверкой и не обходить ограничения через привилегированный запуск кода PR. Политика одобрения fork PR также может требовать действия владельца.

После появления workflow выполнить контрольный push и обновление PR именно через штатный looper; проверить событие, ветку, commit SHA и результаты checks. При PR-trigger GitHub может проверять merge ref: сверить его с актуальным head PR. Для `main` рекомендовать required checks `tests` и `lint` после первого успешного запуска; изменение ruleset требует прав владельца и не входит в автоматическую правку репозитория. Looper должен ждать checks актуальной ревизии, не считать старый зелёный статус разрешением на merge.

### 5. Минимальные проверки качества

Для первой версии использовать уже имеющийся Flake8: `poetry run flake8 . --select=E9,F63,F7,F82 --exclude=.git,.venv`. Это узкий обязательный набор ошибок синтаксиса и явно ошибочных конструкций без массовой правки стиля. Устранить найденные ошибки минимальными изменениями; не скрывать их blanket-ignore.

Ruff полезен как последующая замена Flake8/Black, но одновременное внедрение двух линтеров не нужно. Полный формат-check, типизацию, pre-commit, actionlint, dependency audit и Dependabot рассмотреть отдельно после стабильного CI. Для текущего небольшого проекта приоритет — тесты, базовый lint, короткие логи и воспроизводимость. Изменение lock-файла допустимо только для выбранного средства сетевой изоляции, с проверкой отсутствия массовых обновлений.

Обновить `README.md` и `tests/README.md`: команды, границы smoke-теста, реальные skips, API opt-in, ограничения авторизации looper. При изменении обязательных команд согласовать `AGENTS.md`.

## Риски

| Риск | Решение |
| --- | --- |
| Старые зависимости не устанавливаются | Проверить Python 3.10/Poetry 1.8.2; записать точную ошибку, не обновлять весь стек вслепую. |
| Исправление тестов превращается в переписывание мира | Разделить проверку игрового цикла и контракт загрузчика; архитектуру сигналов вынести отдельно. |
| Моки скрывают ошибки ECS/выхода | Настоящие Registry, Console, InGame; наблюдаемые glyph и освобождение контекста. |
| Случайный платный API-запрос | Явный opt-in, блокировка сети до collection, изоляция окружения и правильные точки мокирования. |
| Проверки looper не появляются | Проверить источник событий и тип авторизации; потребовать фактический run на контрольном обновлении. |
| Линтер создаёт большой несвязанный diff | Использовать существующий Flake8 с узким набором правил, форматирование отложить. |

## Валидация и критерии приёмки реализации

- [ ] Чистый checkout устанавливается из lock-файла; baseline и исправленные исходные ошибки записаны отдельно от регрессий.
- [ ] Offline-набор проходит без ключей, дисплея и `world_model.json`; API-тесты не выполняются по умолчанию даже с фиктивным ключом. Попытка сети немедленно падает.
- [ ] Smoke-тест проверяет настоящий старт, один кадр, реальный `Quit` и освобождение контекста; поломка каждого из этих действий делает соответствующую проверку красной.
- [ ] Ошибки старта/загрузки не маскируются; сохранившиеся ограничения и пропуски перечислены, нет новых исключений ради зелёного результата.
- [ ] Push обычной ветки, PR в `main` и штатный push/PR looper создают ожидаемые проверки. Проверено обновление PR новым коммитом; в отчёте есть ссылки на runs. При невозможности проверить looper этот критерий остаётся невыполненным.
- [ ] Ошибка теста/lint даёт failed check; отменяется только устаревший запуск соответствующего события; артефакты доступны при падении тестов.
- [ ] Документация соответствует workflow, `git diff --check` проходит; секретов и сгенерированных миров в diff нет.

Целевые команды после реализации изоляции (дополнить выбранным механизмом запрета сети, включённым по умолчанию):

```bash
poetry install --no-root
poetry run python -m pytest tests/test_game_startup.py -v
poetry run python -m pytest tests/ -v --ignore=tests/test_world_generator_e2e.py --cov=main --cov=game --cov=llm --cov-report=term-missing --cov-report=xml --junitxml=test-results.xml
poetry run python -m llm.generators.cli --help
poetry run flake8 . --select=E9,F63,F7,F82 --exclude=.git,.venv
git diff --check
```

## Проверка этой спецификации

Изучены README, первичное ревью, настройки Poetry, игровые модули, генераторы и тестовые фикстуры. Пути существующих файлов и положения плана сверены с кодом; новые файлы явно обозначены как будущие. В окружении планирования Poetry отсутствует: `poetry install --no-root`, стандартный pytest с исключением API-файла и CLI `--help` завершаются `poetry: command not found`. Установка, тестовый baseline и CLI здесь не подтверждены. Игра и реальная генерация не запускались; runtime-код и зависимости этим PR не меняются.
