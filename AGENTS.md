# Инструкции для автоматизированной разработки

Этот файл применяется ко всему репозиторию. Сохраняйте стандартные имена `AGENTS.md` и `README.md`; не создавайте дубликаты, отличающиеся только регистром.

## Начало работы

1. Прочитайте `README.md` и `docs/INITIAL_REVIEW.md`, затем код и тесты затрагиваемого модуля.
2. Проверьте `git status`, текущую ветку и существующие изменения. Не перезаписывайте чужую работу.
3. Используйте зависимости из `pyproject.toml` и `poetry.lock`: `poetry install --no-root`, затем команды через `poetry run`. Не меняйте зависимости и lock-файл без необходимости для задачи.
4. До изменения поведения зафиксируйте baseline соответствующих тестов. Документы `ARCHITECTURE.md`, `MODULE_CONTRACTS.md`, `NEXT_STEPS.md` и `project_analysis.md` частично устарели: сверяйте утверждения с реализацией, а несовпадения описывайте явно.

## Границы модулей

- `main.py` управляет жизненным циклом TCOD; `g.py` хранит общее состояние. Изменения здесь требуют проверки событий, рендеринга и завершения приложения.
- `game/` содержит ECS и перевод данных мира в игровые сущности. Сохраняйте согласованность компонентов, тегов и запросов к Registry.
- `llm/generators/` разделяет генерацию темы, названия, сюжета, механик и предметов. `WorldGenerator` оркестрирует их; `llm/world.py` сохраняет старый интерфейс `World`.
- `llm/models.py` задаёт сериализуемые структуры. При изменении схемы проверяйте генераторы, JSON, загрузчик и тесты вместе. Не предполагайте, что описание поля автоматически валидирует его содержимое.
- Не считайте планы готовыми модулями: `utils/`, `config/`, `llm/components.py` сейчас отсутствуют. Не добавляйте их только ради соответствия старой документации.

## Реализация

Делайте минимальное связное изменение для задачи. Сохраняйте стиль окружающего кода и аннотации типов. При исправлении поведения добавляйте проверку воспроизводимого сценария, включая ошибочный ввод, где это уместно. Для правок только документации проверяйте пути, ссылки, команды и соответствие коду; искусственные тесты текста не нужны.

Не заменяйте реальные проверки заглушками и не скрывайте существующие падения через `skip`. Ошибки вне задачи фиксируйте в отчёте отдельно от внесённых регрессий. Не обещайте fallback, потокобезопасность или готовый игровой мир без реализации и тестов.

## Проверки

```bash
poetry run python -m pytest tests/ -v --ignore=tests/test_world_generator_e2e.py
poetry run python -m llm.generators.cli --help
git diff --check
```

Сначала запускайте затронутые тесты, затем более широкий набор при изменении поведения. Список текущих ограничений находится в `tests/README.md`. Файл `test_world_generator_e2e.py` содержит реальные API-вызовы; не запускайте его как обычный smoke test. Для автоматических проверок используйте моки в месте использования клиента (например, `llm.generators.base.ChatOpenAI`) и не используйте реальные ключи. Маркеры сейчас не гарантируют сетевую изоляцию всего набора.

Не запускайте генерацию или игру для проверки документации: первая обращается к внешнему API, вторая требует дисплея и незавершённой структуры мира. Если нужную проверку нельзя выполнить, укажите команду, причину и непроверенную область; не называйте её успешной.

## Завершение

Обновите документацию при изменении команд, схем или интерфейсов. Перед коммитом проверьте staged/unstaged diff и untracked-файлы. Не коммитьте `.env`, ключи, локальные окружения, кэши и случайные результаты генерации. В итоговом отчёте или PR опишите изменение, причину, выполненные проверки и известные ограничения. Коммиты должны быть небольшими и относиться к задаче; в истории используются префиксы вроде `fix:`, для документации подходит `docs:`.
