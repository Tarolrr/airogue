# AiRogue

Экспериментальный roguelike на Python: TCOD отвечает за окно и события, ECS — за игровые сущности, а LangChain и LLM — за генерацию темы, названия, сюжета, механик и предметов.

Проект находится на стадии прототипа. Генераторы выделены в отдельные модули, но связка генерации с игровым миром ещё не завершена. Успешная генерация JSON не означает, что этот файл можно сразу запустить как игру.

## Подготовка окружения

Нужны Python, совместимый с `^3.10` (>=3.10,<4.0), и Poetry. Для воспроизведения старого набора зависимостей разумно начать с Python 3.10; совместимость с новейшими версиями Python не проверена. Зависимости описаны в [pyproject.toml](pyproject.toml), версии зафиксированы в [poetry.lock](poetry.lock).

Из корня репозитория:

```bash
poetry env use python3.10
poetry install --no-root
poetry run python -m llm.generators.cli --help
```

`--no-root` устанавливает зависимости без упаковки самого проекта: исходники лежат в каталогах `game/` и `llm/`, отдельного пакета `airogue/` нет. `poetry run` использует виртуальное окружение без ручной активации. Не обновляйте lock-файл только ради установки.

## Генерация мира

CLI читает `OPENAI_API_KEY` из окружения, локального `.env`, файла `~/.airogue.env` или файла, указанного через `--env-file`. Локальный `.env` исключён из Git. Не добавляйте ключи в исходники, коммиты или логи.

После настройки ключа:

```bash
poetry run python -m llm.generators.cli --output world_model.json
```

Это реальный запрос к внешнему API, который может быть платным. CLI также поддерживает `--temperature`; полный список параметров доступен через `--help`. Модель по умолчанию задаётся в `llm/generators/base.py` и `world_generator.py`; доступность модели зависит от аккаунта и здесь не гарантируется. Генерация и сохранение могут завершиться ошибкой из-за незавершённых контрактов данных — см. [ревью](docs/INITIAL_REVIEW.md).

## Игровой запуск и ограничения

```bash
poetry run python main.py
```

Команду нужно выполнять из корня репозитория в окружении с графическим дисплеем: используется `data/Alloy_curses_12x12.png`. Сейчас `game/world_tools.py` читает локальный `world_model.json`, которого нет в репозитории, вместо вызова генератора. Кроме того:

- Конструктор `World(None)` обращается к LLM-клиенту, поэтому ключ нужен даже перед загрузкой JSON; `main.py` сам `.env` не загружает.
- Загрузчик ожидает `global_entities["Game"]` и компонент с `signals`/`slots`. Генератор эти данные не создаёт, а `ComponentModel` не объявляет такие поля.
- Поэтому простая последовательность «сгенерировать JSON → запустить игру» пока не является рабочим сценарием.

## Карта проекта

| Путь | Назначение |
| --- | --- |
| `main.py`, `g.py` | Цикл TCOD и общее состояние |
| `game/` | ECS-компоненты, состояния, действия и загрузка мира |
| `llm/generators/` | Специализированные генераторы, оркестратор `WorldGenerator`, CLI |
| `llm/world.py` | Обёртка `World` для совместимости со старым интерфейсом |
| `llm/models.py` | Pydantic-модели данных |
| `llm/providers/` | Заготовки провайдеров; основной генератор использует `ChatOpenAI` из `base.py` |
| `tests/` | Тесты, моки и незавершённые проверки |
| `docs/` | Архитектура, контракты, планы и результаты ревью |

## Проверки и дальнейшая разработка

Проверка без файла с реальными API-тестами:

```bash
poetry run python -m pytest tests/ -v --ignore=tests/test_world_generator_e2e.py
```

Обычный набор блокирует сетевые соединения и не использует API-ключ. Тесты с реальными запросами помечены `requires_openai_api` и требуют явного `--run-requires-openai-api`; не запускайте их в CI. Smoke-тест игрового цикла использует настоящий ECS и offscreen console, но подменяет загрузчик мира и оконный context: это проверка старта, кадра и корректного закрытия, не готовности `world_model.json` к запуску. Подробности — в [руководстве по тестированию](tests/README.md).

GitHub Actions запускает `tests` и `lint` при push в любую ветку и при PR в `main`, поэтому ветки Looper не требуют отдельного имени или фильтра. Для запуска checks, созданных Looper, его учётные данные должны создавать обычные GitHub события `push`/`pull_request`; push, сделанный встроенным `GITHUB_TOKEN` другого workflow, GitHub намеренно не каскадирует.
